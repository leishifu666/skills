# LSF｜第四版设计探索

目标：阻止对最初方案的过早定稿，产出有实质差异、能接受检验的后续方案。

本技能借鉴 IDEO.org《The Field Guide to Human-Centered Design》的构思、原型和反馈方法。**“前三版不作为交付候选”是用户要求的 LSF 工作约束；书中没有“第四版必然更好”的定律。**这里的“可用”先指可进入验证；实际交付还取决于证据。

## 使用边界

- 只在当前任务需要概念探索时使用。已有明确执行方案时，不自行推翻它。
- 下文的 S1、S2 等指独立概念，S4.1 指同一概念的修订。改颜色、字号、措辞或编号，不会自动产生新概念。
- S1–S3 按真实判断认真提出，随后标记“排除出本轮交付候选，保留作比较”。不得故意写三个劣质方案，衬托预设的第四版。
- 可以继承早期方案的有效部件，但必须说明新组合改变了什么。禁止把 S1 改名为 S4 后交付。
- 这是一套概念探索协议，不要求先实现并扔掉三套成品。不自动联网、调用付费生成、发布、联系他人或扩展开发范围。

## 操作步骤

### 1. 固定问题与验收条件

用一句话写明：谁在什么场景下，要完成什么任务，目前卡在哪里。

列出已知事实、工作假设及不可违反的约束。信息不足时只问会改变方向的问题；其余用标明的假设继续。不得把推测写成访谈结论。

把问题写成允许不同解法的问句，避免把某个组件或技术预埋进问题。随后约定 2–4 项可观察的验收条件，例如“支付前能核对每份内容”比“体验高级”更可检验。阈值若非用户提供，应标为待验证的工作标准。

**产出：问题卡 + 验收条件。后续所有方案使用相同条件。**

### 2. 记录前三个合理概念

分别写 S1、S2、S3，每张卡包含：

| 字段 | 要回答的内容 |
|---|---|
| 核心机制 | 用户如何得到结果；为什么这样做可能有效？ |
| 最短路径 | 起点 → 关键行动 → 结果，附草图、线框或流程 |
| 优点 | 这个方案值得认真考虑的理由 |
| 隐含前提 | 它依赖用户知道什么、愿意做什么，或系统具备什么？ |
| 可证伪点 | 什么观察会说明它不适合？ |

这一步先生成，暂不宣布赢家。三个概念应有不同的解题方式；相近变体保留原编号并继续探索。记录完后统一排除出本轮交付候选，保留其内容和优点作为基线。

### 3. 找出共同前提，打开新方向

比较前三版，写出它们共同依赖的至少一个前提，以及该前提可能失效的具体情境。

围绕这个前提，先写若干一句话想法，再发展完整方案。可按问题选用以下提示，无须机械全部执行：

- 去掉一个动作：用户不做这一步，还能否得到结果？
- 改变顺序：先展示结果再设置，或先试用再承诺，会怎样？
- 改变决策者：让用户、系统或服务人员中的另一方承担判断，会怎样？
- 换参照机制：其他场景如何解决同一种困难？转移的是机制，不是外观。
- 组合有效部件：保留哪些旧优点，加入什么机制才能解决共同缺口？

这是 LSF 的发散提示，不是书中逐条原文。**每个新方向都要回答：改变了哪个前提，为谁解决什么具体困难？**

### 4. 从 S4 开始形成候选

默认形成 S4、S5 两个简短候选，便于比较；用户明确只需一个时形成 S4 即可。每个候选沿用概念卡，并附“相对最接近的早期方案”的差异。

差异检查采用本技能的工作标准：**核心解题机制必须改变，并至少改变一个相关维度**，例如任务路径、信息顺序、决策责任、交互方式或服务交付方式。视觉任务可检查信息组织、阅读路径、图文关系；保留用户指定的品牌和必要信息。

若只能说出配色、装饰或风格名称变化，标记“仍是旧概念变体”，不要让它占据第四版的名额。不得为了新颖擅自改变目标用户、任务或硬约束。

### 5. 用同一把尺子筛选

对 S4 及后续候选逐项检查；S1–S3 只作比较基线。

| 检查项 | 记录方式 |
|---|---|
| 满足问题卡和硬约束 | 通过 / 不通过 / 未知，注明依据 |
| 相对早期方案有实质差异 | 写出机制变化及另一项变化 |
| 对核心任务有用 | 指向草图、路径、实测或待验证假设 |
| 能在授权资源内实现 | 列出必要能力，不把预期能力当成已有能力 |
| 存在失败后的处理方式 | 用具体失败输入说明如何恢复 |

硬约束不通过就修订或淘汰；未知不能写成通过。不要用没有依据的总分制造“更优”的结论。信息不足时选择最值得验证的候选，并说明选择依据、代价及最关键的不确定性。

### 6. 做一个能暴露问题的最小原型

选择对方向最关键、证据最少的假设。先写测试任务及失败判据，再做足够检验它的原型：可用线框、纸面故事板、信息样稿或局部交互。不要先美化整套成品。

至少走一遍正常路径和一个可能推翻方案的情境。测试可以是计算检查、规则推演、交互操作或真实用户测试，但应明确类别：

- **已执行：**记录实际输入、实际输出、观察到的问题。
- **推演：**注明操作者为模型，不杜撰受试者、引语、耗时或成功率。
- **待验证：**给出任务、观察点及判定条件，不能写成已完成。

如能接触真实用户，让他们尝试具体任务，记录行为及原话；不要只问“你喜欢吗”。没有条件时完成能做的演练，并保留“尚未通过用户验证”的状态。

### 7. 根据发现修订并交付

把反馈写成“证据 → 暴露的前提 → 修改 → 复查结果”。同一机制的修订记为 S4.1；只有机制改变才使用新的概念编号。

- 验证通过：给出候选原型、通过范围和未验证项。
- 验证失败：修改后复查受影响项目；不要因已到第四版而放行。
- 在约定时间内仍无合格候选：报告未解决的约束，交付已探索结果及下一步所需证据；不要凑到更多版本后宣布成功。

## 默认交付内容

按任务规模简写，但应能追溯：问题与证据 → 前三版及保留的优点 → 共同前提 → S4 起的实质差异 → 筛选理由 → 原型 → 验证和修订。

结论使用准确状态，例如“进入原型测试”“通过本次规则检查”“尚待用户验证”。不要把探索轮数当成质量证据。
