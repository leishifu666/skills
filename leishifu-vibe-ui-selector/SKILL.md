# 雷师傅 Vibe UI 方案选择器

## 总览

在视觉、交互或动效方向还没有完全确定时，先生成一个可交互的 HTML 选择页，让用户在真实手感里选方向，再继续正式实现。

默认产物是一个 HTML 选择页：5 个由 AI 设计的方案，加 1 个可 DIY 微调的方案。用户可以点击选择，并一键复制选择结果。

## 触发条件

使用本技能，当出现以下任一情况：

- 用户明确要求“出几个方案”“给我 HTML 让我选”“先看效果”“做个选择页”“视觉方向给我选”。
- 用户说“换风格”“换一版感觉”“感觉还没定”“样式还没定”“出一些给我选”“给几个方向”“几种动效/样式”“我选一个”“先不要正式改，先让我选”。
- 用户在小红书封面、海报、落地页、组件、卡片、按钮、导航、仪表盘等视觉产物里表达审美不确定或不满意。
- 任务涉及 UI 视觉、布局位置、组件形态、按钮样式、动效、hover/active、滚动交互、转场、视觉密度等不确定选择。
- 继续直接实现会把审美、交互手感或最终风格锁死，而用户还没有确认方向。

不要用于纯技术确认，例如是否运行测试、是否读取文件、是否继续安装依赖、是否修复明确 bug。

### 路由优先级

当一句话同时命中“HTML/页面/封面/组件实现”和“换风格/给我选/出几个方向”时，本技能优先于普通前端实现技能。先生成选择页，等用户选定后再正式改代码。

必须拦截以下真实高频句式：

- “我想要换风格，你出一些给我选”
- “这个封面方向不对，给我几个方案”
- “先别做最终版，做几个预览让我挑”
- “小红书封面换几个风格看看”
- “按钮/卡片/导航的样式给我几种选择”

## 标准流程

1. 先快速判断需求清晰度。
   - 如果目标已经清楚，用 1-2 句话复述理解，然后直接生成 HTML 选择页。
   - 如果目标仍模糊，先做苏格拉底式追问，直到有 95% 以上把握再生成。
   - 如果用户的核心诉求是“换风格并给我选”，不要先输出纯文字方案；直接进入选择页生成。

2. 若需要追问，严格遵守：
   - 每次只问一个问题。
   - 提问前先用一句话说明为什么要问。
   - 每个问题至少给 A/B/C/D 四个选项。
   - 最后一项永远是 `D. 其他（请自行补充）`。
   - 根据用户回答动态调整下一问，不按固定问卷机械推进。

3. 生成前先理解当前项目风格。
   - 优先查看已有页面、组件、CSS、设计系统、主题变量、动效库和图标库。
   - 保持方案属于当前项目，而不是脱离上下文的漂亮样板。

4. 联网参考设计与动效库。
   - 优先级：21st.dev、Animata、Motionary。
   - 备用参考：Aceternity UI、Magic UI、React Bits、motion.dev。
   - 动效实现还要参考 GSAP，尤其是复杂时序、滚动、跟随、磁吸、拖拽、文字分解、入场编排。
   - 尽量寻找可复用代码、组件结构或实现思路；结合当前项目重新改造，不要机械照搬。
   - 如果网络不可用，明确说明无法实时参考，然后基于已知模式继续。

5. 生成 HTML 选择页。
   - 默认使用单文件 HTML + CSS + 原生 JS，确保可直接打开。
   - 如果当前项目已经使用 React、Tailwind、Framer Motion、GSAP 等栈，并且借用项目栈更合适，可以按项目栈生成预览。
   - 文件位置按环境选择：
     - 标准项目仓库：放在 `.codex/previews/`。
     - 临时 HTML/artifact 工作区且已有 `outputs/`：放在 `outputs/`。
     - 两者都没有：创建 `.codex/previews/`。
   - 命名为 `choice-preview-YYYY-MM-DD-HHMM.html`。
   - 如果用户要求修改已有预览，不覆盖旧文件；复制为新版，例如 `choice-preview-YYYY-MM-DD-HHMM-v2.html`、`-v3.html`。

🔴 CHECKPOINT · 用户没有选定前，停止在“选择页”层面。不要修改正式项目代码，不要把某个方案直接做成最终版。

## HTML 选择页要求

必须包含 6 个真实不同的方案：

- A-E：5 个 AI 主动设计方案。
- F：1 个 DIY 方案，允许用户按当前任务最关键的参数自由微调。

每个方案都要有真实差异，不能只换颜色或文案凑数。差异可以来自视觉层级、组件结构、动效节奏、布局密度、交互反馈、信息组织、品牌感、空间感或技术实现方式。

DIY 方案的可调参数要按任务自适应选择，不要固定塞满控件：

- 按钮/控件：颜色、圆角、边框、阴影、图标、hover、active、按压感。
- 排版：字号、字重、字间距、行高、段落密度、标题比例。
- 卡片/容器：背景、边框、投影、玻璃感、间距、层级、图片比例。
- 动效：速度、强度、延迟、缓动、跟随范围、弹性、过渡方式。
- 布局：列数、排列方式、吸附位置、固定/跟随、紧凑/标准/宽松。

选择页必须支持：

- 点击任意方案后出现明确选中状态。
- 一键复制选择结果，格式类似：`我选择方案 C：方案名。补充：...`
- DIY 当前参数也能进入复制文本。
- 桌面和移动端都能正常查看。
- 关键交互不依赖外部构建流程。

## 验证要求

生成后至少做一次可审计检查：

1. 用浏览器、Playwright、Chrome、截图工具或项目已有预览工具打开选择页。
2. 静态验收：HTML 至少有 6 个方案、选中态、点击处理（如 `selectOption`）、复制按钮、DIY 控件和参数序列化。
3. 交互验收：点击任意方案后结果文本变化，DIY 改动能写入复制文本。
4. 确认移动端宽度没有横向溢出，主要文字没有挤出卡片。
5. 如果当前环境无法浏览器验证，在回复里明确写“未做浏览器验证”，并给出手动检查项。

## 视觉质量标准

- 先贴合项目已有风格，再加入设计库里的动效和细节灵感。
- 做出能指导落地的真实界面片段，而不是抽象色卡或空洞说明。
- 按用户场景控制密度：工具型产品偏清晰高效，官网/营销页可更有表现力，创意实验可更大胆。
- 避免单一色相堆叠、模板化渐变、大面积装饰性光斑、无意义卡片堆砌。
- 控件尺寸、文字行高、容器宽度要稳定，hover 或动态文本不能挤乱布局。
- 如果使用外部灵感或组件模式，在回复里简短说明参考来源和改造方向。

## 用户不满意时

当用户要求调整 HTML 预览：

1. 保留旧版本，不直接覆盖。
2. 基于旧 HTML 创建副本并修改。
3. 新版文件名追加版本号，例如 `-v2`。
4. 回复时说明新版路径，以及主要修改了哪些方向。

## 用户选定后

用户回复选择结果后：

1. 复述用户选择的方案和关键参数。
2. 按选中方向修改正式项目代码。
3. 使用项目已有组件、样式体系和技术栈落地。
4. 完成后运行合适的验证，例如构建、测试、浏览器预览或截图检查。
5. 验证通过后清理对应临时 HTML 预览文件；若用户要求保留，则不要删除。

## 输出习惯

生成预览后，回复要简洁说明：

- HTML 文件的绝对路径或可打开路径。
- 6 个方案的极简索引。
- 用户下一步只需要打开文件、点击方案并复制选择结果。

不要在聊天里用长篇文字替代 HTML 选择页。

## 失败模式与兜底

| 触发条件 | 一线处理 | 仍失败时兜底 |
|---|---|---|
| 已经在聊天里列了文字方案，但没有生成 HTML 选择页 | 承认漏触发，立即补生成 `choice-preview-*.html` | 用已有文字方案作为 A-E 初稿，补 F DIY 和复制结果 |
| 找不到项目目录或 `.codex/previews/` 不存在 | 按环境创建 `.codex/previews/` 或使用现有 `outputs/` | 生成到当前工作目录的 `outputs/` 并回复绝对路径 |
| 联网设计参考不可用 | 明确说明无法实时参考，继续用本地经验生成 | 在回复里标注未联网，不要因此只给文字方案 |
| 浏览器验证工具不可用 | 做静态自检：6 个方案、选中态、复制文本、移动端 CSS | 回复里列出未验证项和用户可手动打开的路径 |
| 用户只回复一个字母 | 复述方案和参数，进入正式实现 | 如果字母不存在，要求用户从 A-F 重新选 |

## 常见误区

- 不要只在聊天里列 6 条文字方案，必须生成可交互 HTML。
- 不要说“我先给你几条路线，你选了我再做预览”；用户已经要求给我选时，预览就是本轮产物。
- 不要跳过项目风格观察，直接套外部组件库审美。
- 不要把 DIY 做成固定控件堆，要根据当前任务选择最关键的调节项。
- 不要覆盖用户已经看过的旧预览；修改时创建新版副本。
- 不要在用户选定后直接声称完成；必须落地到正式代码并验证。
