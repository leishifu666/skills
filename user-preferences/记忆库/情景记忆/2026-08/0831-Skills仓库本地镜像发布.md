# 2026-08-31 Skills 仓库本地镜像发布

## 事件目标

雷师傅要求检查本机所有 Skills，并将 Skills 与 Codex 全局规则上传到各自专用仓库。执行过程中进一步明确：Skills 发布一切以本地为准，远端旧 Skills 应清理后由本地集合完整替换。

## 执行时间线

1. 读取用户偏好、技能管理和危险操作保护规则。
2. 盘点本机 Skills、嵌套 Git 仓库、专用发布仓库及 Codex 规则差异。
3. 识别到标准更新扫描器只覆盖带 GitHub 元数据的少量 Skills，并补充检查嵌套仓库远端状态。
4. 发现正在使用的 Skills 工作目录有大量历史改动，因此改用干净的专用同步仓库作为发布工作区。
5. 雷师傅确认以本地为准，并进一步选择“清空远端旧 Skills 后上传本地镜像”。
6. 排除 `.system`、嵌套 `.git`、真实 `.env`、缓存、日志、`node_modules`、本机构建程序和超大文件。
7. 将 83 个本地有效 Skills 镜像到发布工作区，删除 86 个本地不存在的旧目录。
8. 使用普通 Git 提交保留删除历史，并将最终内容快进推送到同步分支和默认 `main` 分支。
9. 同步 Codex 全局规则到独立仓库。
10. 最终验证发现 `document-illustrator` 仍是 `160000` 子仓库指针，追加修复提交将其转换为普通文件目录。
11. 远端最终验证通过：本地 83、远端 83、缺失 0、额外 0，两个仓库工作区均干净。

## 关键决策

- 本机可识别 Skills 集合是发布准本，上游变化只记录，不自动合并。
- 删除远端旧 Skills 使用普通提交，不强推，确保可从 Git 历史恢复。
- 默认分支 `main` 必须与同步分支同时更新，避免仓库首页仍显示旧内容。
- 嵌套 Git 仓库不能只看文件系统，必须检查提交树是否仍记录为 `160000` gitlink。

## 问题与修正

- Windows 默认 GBK 导致 UTF-8 校验器把全部 Skills 误报为读取失败；切换 UTF-8 模式后确认是环境问题。
- 严格校验器的 frontmatter 白名单落后于当前 Codex 实际支持字段，因此没有为了通过旧校验器而破坏现有元数据。
- 首次推送命令超过等待时限；没有盲目重推，而是先查询远端引用，确认实际已经成功。
- 第一次最终数量检查发现少 1 个 Skill，定位为子仓库指针并追加修复。
- 自我迭代时发现 `smart_stitch.py` 首次追加与后续更新的空行格式不一致；已统一写入格式，并通过连续两次运行哈希不变的幂等性验证。
