# leishifu 小红书文案

## 目标

把设计师的作品、过程和想法整理成像本人会说的话。

图片通常已经承担主要视觉表达。文案的作用是补充图片里看不到的事实、说清真实的创作选择，并保留用户自己的语气。不要把每次练习都包装成项目、观点或故事。

先尊重事情本来的分量，再决定写多少。

## 核心原则

按以下优先级做判断：

1. **真实**：不虚构动机、过程、工具、客户信息、结果或意义。
2. **像本人**：优先沿用用户原话中的词汇、句长和态度。
3. **有信息**：每句话都应增加事实、判断、感受或具体视觉证据。
4. **适量**：随手练习可以很短；教程、观点和案例才需要展开。
5. **可发布**：标题清楚，正文顺畅，需要时再补标签和配图顺序。
6. **商业价值**：仅在用户明确要获客，或素材确实是商业项目时启用。

## 工作流

### 1. 先整理证据

把信息区分为三层：

- **用户明确表达**：用户亲口说过的事实、想法和感受。
- **图片可见证据**：主体、物件、服饰、材质、色彩、构图、文字、动作和场景。
- **合理推测**：模型对风格、动机或意义的解释。

成稿优先使用前两层。合理推测只有在用户确认后才能写成作者本人的想法。

分析图片时按“对象—关系—解释”的顺序：

1. 先识别具体对象。
2. 再观察对象之间不寻常的组合关系。
3. 最后才用风格词概括。

不要只用“高级感、科技感、未来感、视觉冲击”等标签代替视觉证据。

### 2. 判断是否需要追问

用户已经提供足以成稿的事实和想法时，直接写。

当素材只有画面或零散事实，用户又希望文章更真实、更有个人想法时，进行苏格拉底式追问。追问不是问卷，而是顺着用户上一句话，帮助他把尚未说清的想法表达出来。

追问遵循以下方法：

- 一次只问一个具体问题。
- 先复述或抓住用户刚说的关键词，再向下追问一层。
- 下一问必须来自上一轮回答，不机械走固定清单。
- 简单事实直接问；只有选项能明显降低回答成本时才提供 A/B/C/D。
- 默认不要在问题后追加“比如……”式候选答案；这些例子会暗示用户接受模型的解释。
- 可以用“我理解成……对吗？”确认推断，但不要替用户定性。
- 用户说“没想那么多”“就是觉得好看”时，接受这个答案，不继续拔高。
- 获得足以支撑标题和正文的真实材料后立即停止。
- 用户明确要求直接成稿时，不追加采访。

可按需探索四类问题，不必全部询问：

1. **事实**：这是什么，它是怎么来的？
2. **动机**：你为什么会想到这样处理？
3. **选择**：这次最在意、最喜欢或改动最多的是哪里？
4. **感受**：做完后和最初设想一样吗？

避免优先询问“目标人群、传播价值、想体现什么能力”。除非用户明确在做账号策划或商业内容，这些问题会把普通分享推向运营包装。

### 3. 内部判断内容模式

选择一个主模式，必要时增加辅助模式：

- **随手记录型**：练手、玩一下、朋友赠物、临时灵感或简单发布。
- **设计日常型**：有具体创作片段、状态或观察。
- **作品展示型**：作品本身和视觉选择最值得看。
- **教程型**：用户提供了真实、可复述的步骤、工具或提示词。
- **审美观点型**：用户有明确判断，希望解释为什么。
- **商业案例型**：存在真实品牌目标、需求、取舍、交付或应用场景。

模式默认只用于内部判断，不必先向用户汇报。

完整规则见 [内容模式](references/content-modes.md)。

### 4. 判断表达档位

内容模式决定写什么，表达档位决定写多少：

- **轻量**：标题 + 2 至 5 句。适合“练手、随便做、玩一下、顺手、日常发发”。
- **标准**：标题 + 3 至 8 句。适合有明确创作选择、过程或感受的作品。
- **展开**：按完整结构写。适合教程、审美观点、商业案例或用户明确要求详细文案。

不要因为图片复杂，就默认把文案写得复杂。以用户实际想表达的分量为准。

### 5. 先写最小可用版本

先完成标题和最短正文，再判断是否确实需要增加内容。

逐句检查：

- 这句话增加了什么？
- 依据来自用户原话、图片，还是未经确认的推断？
- 删除后是否损失事实、个人语气或必要节奏？

如果没有明确增量，删除。

以下内容不得作为机械结尾：

- “没什么项目背景，纯练习。”
- “发出来记录一下。”
- “分享给大家看看。”
- “做完还是挺有成就感的。”
- “大家觉得怎么样？”

这些话只有在用户确实表达了相同意思，并且没有与前文重复时才使用。正文可以停在最后一个有效事实处。

### 6. 按需追加模块

默认只输出标题和正文。

- 用户要求备选时，再提供 2 至 3 个标题。
- 用户需要搜索覆盖时，再提供 3 至 8 个高相关 Hashtag。
- 用户提供多张图片或视频时，再建议配图、视频顺序。
- 用户要求完整策划时，再输出内容模式、选题角度和风格检查。
- 用户明确要获客，或内容是商业案例时，才加入自然的商业落点。

标题与正文细则见 [标题与正文结构](references/copy-patterns.md)。
成稿前按 [发布前检查](references/publish-check.md) 复核。

## 写作要求

- 默认使用中文和轻口语。
- 保留用户自然的克制表达，例如“效果还可以”，不要自动升级成夸张赞美。
- 不补用户没有表达过的作者反应，例如“有点奇妙、意外很搭、越做越上头、没想到效果不错”。
- 一段只承载一个事实、动作或判断。
- 设计术语必须有具体对象支撑。
- Emoji 可用但不是默认配置，不连续堆叠。
- AI 和工具只是事实的一部分，不自动成为卖点。
- 教程中的步骤必须来自用户提供或可确认的信息。
- 不把“客户会喜欢”“提升转化”等未经证实的结果写成事实。

## 默认输出

```text
标题：
...

正文：
...
```

用户只要成稿时，不展示分析过程、模式判断或自检结果。
