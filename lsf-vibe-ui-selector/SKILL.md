# LSF Vibe UI 方案选择器

除非用户明确要求其他语言，使用中文提问、解释和报告。代码、API、CSS 属性、标准名称及必要术语保留原文。

视觉、交互或动效方向未定时，先生成一个可交互的 HTML 选择页，让用户在真实手感里选方向，再继续正式实现。默认产物是 5 个 AI 设计的方案加 1 个可 DIY 微调的方案，用户点选并复制选择结果。

## 真实差异，不是换皮

每个方案都要有真实差异，不能只换颜色或文案凑数。差异来自视觉层级、组件结构、动效节奏、布局密度、交互反馈、信息组织、品牌感、空间感或技术实现方式。只换色调的方案选不出方向，这轮就白做了。方案能指导落地，是真实界面片段，不是抽象色卡或空洞说明。

## 触发条件

使用本技能，当出现以下任一情况：

- 用户明确要求"出几个方案""给我 HTML 让我选""先看效果""做个选择页""视觉方向给我选"。
- 用户说"换风格""换一版感觉""感觉还没定""样式还没定""出一些给我选""给几个方向""几种动效/样式""我选一个""先不要正式改，先让我选"。
- 用户在小红书封面、海报、落地页、组件、卡片、按钮、导航、仪表盘等视觉产物里表达审美不确定或不满意。
- 任务涉及 UI 视觉、布局位置、组件形态、按钮样式、动效、hover/active、滚动交互、转场、视觉密度等不确定选择。
- 继续直接实现会把审美、交互手感或最终风格锁死，而用户还没有确认方向。

不要用于纯技术确认，例如是否运行测试、是否读取文件、是否继续安装依赖、是否修复明确 bug。

当一句话同时命中"HTML/页面/封面/组件实现"和"换风格/给我选/出几个方向"时，本技能优先于普通前端实现技能：先生成选择页，等用户选定后再正式改代码。

## 1. 判断需求清晰度

- 目标已经清楚：用 1-2 句话复述理解，直接生成 HTML 选择页。
- 目标仍模糊：先做苏格拉底式追问，直到有 95% 以上把握再生成。
- 核心诉求是"换风格并给我选"：不要先输出纯文字方案，直接进入选择页生成。

## 2. 追问规则

每次只问一个问题。提问前先用一句话说明为什么要问。每个问题至少给 A/B/C/D 四个选项，最后一项永远是 `D. 其他（请自行补充）`。根据用户回答动态调整下一问，不按固定问卷机械推进。

## 3. 理解当前项目风格

优先查看已有页面、组件、CSS、设计系统、主题变量、动效库和图标库。方案属于当前项目，而不是脱离上下文的漂亮样板。

## 4. 联网参考设计与动效库

优先级：21st.dev、Animata、Motionary。备用参考：Aceternity UI、Magic UI、React Bits、motion.dev。动效实现参考 GSAP，尤其是复杂时序、滚动、跟随、磁吸、拖拽、文字分解、入场编排。尽量寻找可复用代码、组件结构或实现思路，结合当前项目重新改造，不要机械照搬。网络不可用时明确说明无法实时参考，然后基于已知模式继续。使用了外部灵感或组件模式时，在回复里简短说明参考来源和改造方向。

## 5. 生成 HTML 选择页

默认使用单文件 HTML + CSS + 原生 JS，确保可直接打开。当前项目已用 React、Tailwind、Framer Motion、GSAP 等栈且借用项目栈更合适时，可以按项目栈生成预览。文件位置按环境选择：

- 标准项目仓库：放在 `.codex/previews/`。
- 临时 HTML/artifact 工作区且已有 `outputs/`：放在 `outputs/`。
- 两者都没有：创建 `.codex/previews/`。

命名为 `choice-preview-YYYY-MM-DD-HHMM.html`。用户要求修改已有预览时不覆盖旧文件，复制为新版，例如 `choice-preview-YYYY-MM-DD-HHMM-v2.html`、`-v3.html`。

🔴 CHECKPOINT · 用户没有选定前，停止在"选择页"层面。不要修改正式项目代码，不要把某个方案直接做成最终版。

六个方案、DIY 参数、交互与复制、验证清单的完整规格见 [choice-page.md](choice-page.md)。

## 6. 验证

生成后至少做一次可审计检查，按 [choice-page.md](choice-page.md) 的验证清单执行。环境无法浏览器验证时，在回复里明确写"未做浏览器验证"，并给出手动检查项。

## 7. 用户选定后落地

用户回复选择结果后：

1. 复述用户选择的方案和关键参数。
2. 按选中方向修改正式项目代码，使用项目已有组件、样式体系和技术栈落地。
3. 完成后运行合适的验证，例如构建、测试、浏览器预览或截图检查。
4. 验证通过后清理对应临时 HTML 预览文件；若用户要求保留，则不要删除。

## 输出习惯

生成预览后，回复要简洁说明：HTML 文件的绝对路径或可打开路径、6 个方案的极简索引、用户下一步只需要打开文件点击方案并复制选择结果。不要在聊天里用长篇文字替代 HTML 选择页。

## 与集合内其他技能的分工

- 设计质量与领域规则归各 `lsf-better-*` 技能所有，本技能不重复定义。方案先贴合项目已有风格，再借用设计库的动效与细节；具体领域判断交给 `lsf-better-layout`、`lsf-better-writing`、`lsf-better-typography`、`lsf-better-colors`、`lsf-better-ui`、`lsf-better-accessibility`，每个方案以 `lsf-better-interface` 的升级触发线为底线。
- 单块 UI 要在真实页面里对比候选：交给 `lsf-variant`，它把若干版本放进页面用选择器切换。本技能用于方向本身未定、需要独立选择页的场合，例如封面、海报、整页、组件风格。
- 组件健壮性压力测试：交给 `lsf-break`。本技能的选择页验证只保证选择页本身可用，不替代组件压力测试。
- 改动后的界面回归审查：交给 `lsf-interface-review` 与 `lsf-better-interface`。本技能在正式实现后不做审查。

## Before you finish

| 误区 | 修正 |
| --- | --- |
| 只在聊天里列 6 条文字方案 | 必须生成可交互 HTML 选择页 |
| 说"我先给你几条路线，你选了我再做预览" | 用户已经要求给我选时，预览就是本轮产物 |
| 跳过项目风格观察，直接套外部组件库审美 | 先读项目已有页面、组件、CSS、设计 token |
| 方案只换颜色或文案凑数 | 让方案在结构、密度、动效、层级等轴上真实不同 |
| DIY 做成固定控件堆 | 按当前任务选择最关键的调节项 |
| 覆盖用户已经看过的旧预览 | 修改时创建新版副本 `-v2`、`-v3` |
| 用户选定后直接声称完成 | 必须落地到正式代码并验证 |
| 环境无浏览器仍声称已验证 | 明确写"未做浏览器验证"并给出手动检查项 |
